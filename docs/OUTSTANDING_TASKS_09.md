### ☑ T44 — Append-only persistence + off-runtime fsync (from T27)
> **Done 2026-09-19 (committed `f8d754e`).** Both halves of T27's residual are closed: a directive now costs **O(directive)** to persist instead of a whole-file rewrite, and the write + fsync happen with the ledger write lock **released** and off the runtime's worker threads. Measured on the same machine and debug profile, on an 88,578-byte canonical ledger: one appended transaction writes **310 bytes** (0.35% of the file); eight successive appends write **1,328 bytes in total** against **711,972 bytes** for the same eight writes on the pre-T44 full-rewrite path — a **536×** reduction, and the `.bean` is not touched at all (asserted byte-for-byte, not by a counter).
>
> **The architecture: a node-private commit journal plus ratio-triggered compaction.** The canonical `.bean` keeps its format and its exact atomic write path (temp + fsync + rename, H-10/CAP-1) — it is deliberately *not* appended to, because a torn `.bean` is a boot brick (boot fails closed on a parse error) and appending in place would trade a survivable failure for an unrecoverable one. Instead a new `ledger::journal` module owns `<ledger>.bean.journal`, an append-only sidecar of framed records: `;;olj <payload-len> <sha256-of-payload>\n<payload>`. The payload is `full_file_serialize(&directives, &[])` for one commit's directives — the *same canonical spelling* the `.bean` uses, so a record's bytes are byte-identical to the slice of the canonical file those directives will eventually occupy, and boot can simply concatenate canonical + payloads and hand the result to the existing `parse_file`. Each header field buys exactly one property: the `;;olj` tag makes a stray concatenation degrade to Beancount comments rather than a parse error; the **length** distinguishes a torn tail (fewer bytes than promised) from corruption (enough bytes, wrong content), which are otherwise the same observation; the **hash** makes "enough bytes, wrong content" detectable at all.
>
> **Two-phase persist.** `LedgerService` splits a write into `prepare_commit()` (in-memory, under the lock, cheap) returning a `PendingCommit`, and `PendingCommit::commit()` (the write and the fsync). `PendingCommit` owns its paths and bytes and holds **no** borrow of the service — that is what makes it `Send + 'static` for `spawn_blocking`, and what makes "the commit cannot race the ledger" a property of the types rather than of caller discipline: the only channel back into memory is the `CommitReceipt` fed to `finish_commit`. New `*_staged` variants (`append_transaction_staged`, `open_account_staged`, `close_account_staged`, `reconcile_file_staged`) mutate without persisting; the existing `*_signing` methods are now those plus an inline `persist_or_reload`, so every synchronous caller and every pre-existing test is unchanged. The SHA-256 of the canonical text also moved into `commit()`, so that `O(ledger)` hash is off the lock with the rest of the I/O.
>
> **Compaction policy (documented constants, no config knob).** `COMPACTION_MIN_CANONICAL_BYTES = 64 KiB`: below it *every* commit rewrites the whole file and **no journal is ever created** — the fsync dominates a sub-64-KiB rewrite either way, so a sidecar would buy nothing and cost a second file, a second failure mode and a lagging canonical file. Above it, `COMPACTION_JOURNAL_RATIO = 2`: fold the journal back once it would reach half the canonical file. Two is derived, not picked — each compaction rewrites `canonical × 3/2` after absorbing `canonical / 2` of journal, so every appended byte costs a bounded ~3 bytes of eventual rewrite *however large the ledger grows*. Compaction is also forced at four other points: the first commit after any boot (see invariant 4), a detected hand edit, a reconcile, an in-place `stamp_signature`, and a torn journal tail. `gl-node` additionally compacts once just after boot (crash recovery) and once at clean shutdown, both best-effort with a `warn!` — the journal is durable and correct either way, so a disk hiccup must not become a refusal to start.
>
> **How each HARD INVARIANT is preserved.** **(1) Durability unchanged for callers.** `commit()` fsyncs before it returns and the mutation `await`s it; there is no ack before the write. The GraphQL broadcast and gossip were additionally moved to *after* the commit — announcing a transaction a failed commit then rolled out of memory would be a lie to every subscriber. `t44_a_stalled_commit_blocks_neither_reads_nor_the_ledger_lock` asserts the mutation waits out a 750 ms stall and that the account is genuinely in the file afterwards. **(2) L-13 preserved.** `recover_failed_commit()` is the old reload, reached from both the prepare-failed and the commit-failed path (prepare can mutate memory — adoption reconciles a hand edit in before serializing). Its reasoning is unchanged and still exact: temp+rename never leaves a half-written `.bean`, and a journal append either lands whole or leaves a torn tail the scanner drops, so a failed commit always leaves the files in their last good state. Two handles are now carried **across** the reload because they are process-scoped machinery and not ledger state: the commit gate (a fresh mutex would silently unserialize any writer holding the old permit) and the test observer. **(3) Cross-node byte-determinism preserved.** Compaction emits `full_file_serialize(dag.directives(), leading_comments)` — literally the pre-T44 `persist` body — so the canonical file is byte-for-byte what it always was. **Zero existing determinism tests were weakened or given compaction calls**: every one of them (T29's 66-permutation `lifecycle_converges_under_every_arrival_order`, T27's `batch_path_is_byte_identical_to_per_entry_path`, CT-9, `test_file_round_trip_stable`, the L-30 suite) runs on a sub-64-KiB ledger and therefore still takes the full-rewrite path unchanged. The new `t44_compaction_is_byte_identical_across_every_arrival_order` **adds** coverage the old tests could not give — 24 arrival orders of four lifecycle directives, each journalled one commit at a time on its own past-threshold ledger, all compacting to identical bytes — so test strength strictly increases. **(4) T35 hand-edit adoption still works.** The exact check (re-read, re-hash, `reconcile_content`) still runs wherever the canonical file is rewritten, which is now precisely the compaction branch of `prepare` — an append cannot erase an edit because it does not touch the `.bean`. A new **O(1) `stat` probe** (size + mtime, `FileMarker`) runs on *every* prepare and escalates to a compaction the moment either moves, so in practice an edit is still adopted at the very next write; what changed is only that the `O(file)` re-read is no longer unconditional. `t44_a_hand_edit_is_adopted_with_journal_records_outstanding` proves the edit and the outstanding journal records both survive. The journal is documented as node-private and unsupported to hand-edit (module doc + `persist_or_reload` rustdoc); a torn FINAL record is warned and dropped, everything else fails closed. **(5) Boot correctness.** `boot` reads canonical ∪ journal, concatenates, and runs the *identical* pipeline — same sort, same cycle pre-scan, same insert loop — rather than a second merge routine, which is what makes the equivalence hold by construction. The journal's read budget is `MAX_LEDGER_FILE_BYTES − canonical_bytes`, and the append path refuses a write whose projected `canonical + journal + record` would exceed the cap, so the compacted file is bounded by the same constant that always bounded the `.bean` and a journal this node wrote can always be booted. **(6) T30 flock story unchanged.** The ledger crate takes no locks; the journal sits next to the `.bean` under the same process-exclusivity assumption, is created `0600` like the `.bean`, and `.gitignore` gained `*.bean.journal` beside `*.bean.lock`. **(7) Concurrency soundness.** A single serialized writer, by construction: `LedgerService::commit_gate()` hands out a `tokio::sync::Mutex` that every write path takes **before** the ledger write lock and holds until the commit is finished or recovered. Appends alone would survive out-of-order commits (journal order **is** arrival order — stated explicitly in `JournalScan::payloads` — and boot sorts the union, which is a G-Set), but a compaction would not: it writes a snapshot from *its* prepare and then deletes the journal, so an append that slipped in between would be erased after its caller had been told it was durable. The gate lives on the service rather than beside it so that every holder of a `SharedLedger` reaches the same mutex with no parameter threaded through `AntiEntropyHandler`, the schema data and `main` — and so no call site can be accidentally left unserialized. `prepare_commit` additionally refuses outright while a commit is in flight (`COMMIT_IN_FLIGHT`), making a forgotten permit a loud error rather than a silent interleave, and `finish_commit` checks the receipt's generation. The lock order is one-way (permit → write lock, never the reverse), so the pair cannot deadlock; readers take neither.
>
> **One behavioural change worth stating plainly: the first commit after any boot is still a full rewrite.** Boot *reads* a file it did not write — a hand-authored ledger, a BOM'd one (L-28), one from an older build — so `canonical_is_current` starts `false` and the first write canonicalises exactly as every pre-T44 persist did. This was found by a test rather than by reasoning: `test_persist_removes_a_byte_order_mark_from_disk` failed when a no-op persist stopped rewriting, and the fix restores the old guarantee precisely instead of special-casing the BOM. The only remaining difference from pre-T44 behaviour is that a genuinely idle `persist_or_reload()` — nothing staged, nothing forced, file untouched — is now a no-op instead of rewriting identical bytes, which nothing that reads the file can observe.

### ☑ T43 — Full M-16 closure (from T26)
> **Done 2026-09-19 (committed `f8d754e`).** Option (a): a bounded CBOR header scan in the new `p2p::cbor_scan`, wired into `WireMessage::decode_checked`, so `MAX_SUPPLY_ENTRIES` is finally enforced against the **wire bytes** instead of against the materialised `Content` tree. No wire-format change, no change to what an honest frame looks like, and every convergence test passes unmodified.
>
> **What was built.** `cbor_scan::supply_entry_count(body)` walks CBOR **headers only** — major type plus additional info, definite lengths — reading no payload bytes except the ≤ 64-byte map keys it has to compare. It parses the top-level map header, iterates its pairs, skips each value it does not recognise with a budgeted iterative skipper, and returns the element count the `entries` array header **claims**. `protocol::prescan_supply_entries` runs it on any frame carrying the `Supply` discriminator and refuses a claim above the cap with the SAME `WireError::BatchTooLarge { kind: "supply", .. }` the post-decode `check_cardinality` would have produced — it is the same rule, only enforced before serde rather than after, and every caller already classifies it. A scan that cannot *answer* returns the new `WireError::FramePrescan(CborScanError)`, deliberately distinct from `CborDecode`: "the guard declined to prove this frame is safe" and "ciborium says these bytes are malformed" are different operational facts and should not share a log line. `SUPPLY_TYPE_DISCRIMINATOR`'s offset rule is now stated once, in `protocol::carries_supply_discriminator`, and T26's `frame_is_rejectable` calls it — the two gates key on the same predicate by construction rather than by two copies of `peek[1..13]`.
>
> **The scan's bounds, and the distance between each one and honest traffic.** `MAX_SCAN_VISITS = 64` headers — the honest path reads **seven** (map header, `"type"` key, `"supply"` value, `"v"` key, its integer, `"entries"` key, the array header). `MAX_SCAN_DEPTH = 4` — the honest path enters **zero** containers, because every value skipped before `entries` is a leaf. `MAX_SCAN_MAP_KEYS = 16` — a `Supply` is a three-pair map and the widest variant (`have_heads` with `more`) is five. `MAX_SCAN_KEY_BYTES = 64` — `"entries"` is seven bytes and the longest key on any variant is `"directive_ids"` at thirteen. The visit budget is the load-bearing one: it is what stops the *guard* becoming the attack, which is the failure a hand-rolled scanner most easily introduces — `scan_rejects_a_wide_skipped_value_on_the_visit_budget` is the case depth alone would have missed (a flat thousand-element array as the value of `"v"`, shallow and cheap to write). The skipper is **iterative with an explicit frame stack, not recursive**, on purpose: recursion over attacker-chosen nesting is a stack-overflow primitive, and a stack overflow is an abort, not an error a serve loop can report.
>
> **Fail-closed, and why that costs an honest peer nothing.** Every rule rejects rather than tolerates — an indefinite-length item, a non-text key, an over-long key, an absurd pair count, nesting or visits past budget, a missing `entries` key, an `entries` value that is not a definite-length array. None is reachable from a conforming sender: serde's derived impls and its internally-tagged `TaggedSerializer` call `serialize_map(Some(n))` / `serialize_seq(Some(n))`, so ciborium emits **definite** lengths for every serde type, and a `Supply` is a fixed three-key map of a text tag, a small integer and one array. That is asserted against real bytes rather than asserted as a claim: `honest_supply_frames_scan_to_their_entry_count` encodes genuine frames at 0, 1, 23, 24, 255 and 256 entries (straddling all three CBOR argument widths), requires the scan to return exactly the entry count, and then requires `decode_checked` to round-trip each one unchanged — an indefinite head or a reordered tag anywhere in that would fail the first assertion. The live `truncate_supply_output_is_always_decodable` property already round-trips up to 256 generated entries through `decode_checked` and is untouched and green, so the sender/receiver agreement H-02 pins is independently re-proved.

> **Field order, read off real ciborium output rather than assumed.** A `Supply` encodes as `a3` · `64 "type"` `66 "supply"` · `61 "v"` `01` · `67 "entries"` · array header — `80` at 0 entries, `81` at 1, `98 18` at 24, `99 01 00` at 256, `99 01 2c` at 300. The tag is first and struct order is preserved, as T26's discriminator already depends on. Every other pre-existing test in the workspace passes **unmodified**, including `paginate_have_heads_pages_are_always_decodable`, which round-trips up to 10,000 ids through `decode_checked` in maximal pages and is the strongest independent evidence the element-skip allowance is sized right.
>
> **Deviations and residuals.** (1) The task allowed "one more `#[test]` in that binary … otherwise a second binary". A second test in the same binary would have raced the process-wide counting allocator against the one being measured, which is exactly why T43 documented a one-test rule — so the rule is now enforced explicitly instead of by convention: both measuring tests hold a `MEASUREMENT` mutex for their whole body, a waiting test holds and allocates nothing, and both measurements stayed clean (forged `Supply` still 0 bytes / honest 1.02×, unchanged from T43's numbers). (2) An honest-traffic measurement was again added beside the attack, for the same reason T43 gave. Neither number is load-bearing (both are diagnostics on a frame that is refused either way), and the tested single-over-cap cases agree exactly.

- **Change:** T26 bounds M-16's amplification for the worst (Want/HaveHeads) vector via the non-Supply frame pre-cap, but a frame *claiming* to be Supply with millions of fake entries still `Content`-buffers before the cardinality cap rejects it. - **Priority:** low — allowlisted-only, and T26's connection cap bounds concurrent decodes.
- **Verify:** a 16 MiB Supply-discriminator frame with millions of entries is rejected without GiB-scale transient allocation (assert bounded peak memory).

### ☑ T42 — Per-peer ALPN connection reuse (optimization; from T23/T24)
> **REVIEW ADDENDUM (2026-09-20, orchestrator).** The multi-stream serve loop as delivered charged the T24 budget per FRAME only, so a zero-byte finished bi-stream — which reaches `accept_bi`, reads as a clean `FinishedEarly(0)` EOF, and carries no frame — cost nothing: a hostile allowlisted peer could loop empty streams forever, holding the connection, its serve task, and its M-16 limiter slot outside the budget entirely (impossible pre-T42, when a connection served exactly one stream). Fixed in review: each accepted stream now charges one budget unit before its frames are read (honest cost: one unit per operation against a budget of 100,000). Pinned by `empty_streams_cannot_hold_a_connection_outside_the_budget`; bug-catch proof fired (charge reverted → all 50 empty streams accepted, test failed; restored → flood cut off at the budget, close code 4). The pre-existing `request_budget_closes_connection_after_limit` arithmetic is unchanged (still 3 round trips on a budget of 6).
> **Done 2026-09-20 (committed `13beca5`).** `fetch_want` and `exchange_with_peer` now take their connection from a shared per-peer cache (`peer_connections::PeerConnectionCache`, one field on `AntiEntropyHandler`, `Arc`-backed so every clone of the handler — router, gossip loop, anti-entropy tick — uses one cache) instead of dialling fresh per operation. **The design:** a global `EndpointId -> Arc<PeerSlot>` map behind a `std::sync::Mutex` held only for the lookup, and per slot a `tokio::sync::Mutex<Option<Connection>>` **held across the dial** — that async mutex IS the dial dedup, so a second caller arriving mid-handshake waits and then finds the finished connection rather than starting its own. The whole acquire (slot wait + dial) is wrapped in ONE connect timeout, so a caller queued behind someone else's dial can never spend two of them and still reports the same `connect timed out` it always did. `Connection` is `Arc`-backed, so concurrent users of a peer each `open_bi()` on a clone and get native QUIC multiplexing.
>
> **The single retry, and where its boundary is.** A pooled connection is `close_reason()`-checked before it is handed out and replaced in-place when it is closed. That check cannot be a guarantee (a connection can die between the check and `open_bi`), so `open_peer_session` re-dials **at most once**, and only when the connection that failed to open a stream came OUT OF THE POOL — a freshly dialled connection that cannot open a stream fails the operation, exactly as it did pre-T42, rather than turning one dial into two against an unreachable peer. The retry sits entirely **before any frame is written or read**: nothing can be issued twice because nothing has been issued. A connection that dies once the protocol is under way is invalidated (so the next operation does not inherit it) and the operation **fails** — anti-entropy is idempotent and would survive a replay, but a silent replay would double the work and the peer's request budget and would hide a real mid-transfer fault. Invalidation drops only the cache's handle, never closing a connection another task is mid-transfer on.
>
> **This required a server change, and that is the honest headline.** The optimization was specified as if the server kept a connection alive until its idle bound — it did not. `serve_anti_entropy` called `accept_bi()` **once** and closed the connection when that one stream EOF'd, so a pooled connection was dead the instant its first operation finished and reuse was unreachable without touching the serve side. It now loops over successive bi-streams. Every limit and value is preserved deliberately: `requests_handled` stays a **per-connection** budget spanning all streams (per-stream would have relaxed T24's cap by however many streams a peer opened), each `accept_bi` wait keeps the same T41 I/O-timeout bound, and streams are served **one at a time** on purpose — concurrency there would multiply the M-16 memory bound, since `ConnectionLimiter` caps concurrent accepted *connections* precisely because each can have a multi-MiB `Supply` decode in flight. The cost is head-of-line blocking between one peer's own overlapping operations, bounded by their I/O timeouts and inflicted by each peer only on itself.
>
> **Server-idle interplay — what the reuse actually buys.** With the loop in place the same I/O timeout (30 s by default; 500 ms under the short-timeout tests) now bounds the wait for *every* stream, so a pooled connection idle past it has already been closed by the server with `accept-bi-timeout` and the next acquire dials again. The win is therefore **within a burst**, never across a quiet gap: overlapping gossip fetches (T23 allows 16 at once, typically all to the same relay) plus an anti-entropy tick against that same peer now share one handshake; ticks closer together than the idle bound reuse; a node syncing once an hour reuses nothing. **With the shipped defaults the periodic loop lands inside the window**: `p2p.antiEntropyIntervalMilliseconds` defaults to 5,000 ms against a 30 s idle bound, so consecutive ticks to a peer keep hitting the same connection, and a quiet node settles at roughly one handshake per peer rather than one every five seconds — refreshed only when the connection is lost, the peer restarts, or the per-connection budget runs out. Change either value and the win moves with them; that is the whole of the interaction. Nothing here widens a server timeout to enlarge that window — those bounds are the M-16/T41 security boundary. Pinned by `a_pooled_connection_idle_past_the_server_bound_is_redialed`, which waits for the server's own close rather than sleeping past a guess at it.
>
> **Bounded state, no new config, no new task:** at most one slot per **allowlisted** peer; `slot_for` prunes de-allowlisted peers on every access, so the cleanup rides the existing access path instead of a background sweep. Dial targets are still allowlist-derived and both call sites still `admits()` first — eclipse/allowlist behaviour is untouched.
>
> **Two server-visible consequences, stated plainly.** (1) The `anti-entropy session complete` close reason is now unreachable: a peer ends a connection it is done with either by closing it (the serve loop returns early, nothing left to say) or by leaving it idle (`accept-bi-timeout`). An idle close after work was served returns `Ok` rather than `Err` — the same timeout still fires and still closes the connection, but reporting an error for every reused connection's ordinary expiry would bury T41's genuine silent-peer case in noise. (2) A long-lived pooled connection accumulates against the 100,000-frame per-connection budget rather than starting fresh per operation; when it is finally spent the server closes with `request-budget-exhausted` and the client's next operation re-dials transparently — the budget still bounds, it is simply amortised now.
>
> **Tests (6 new; existing lifecycle tests unmodified).** `sequential_operations_reuse_one_pooled_connection` (two exchanges *and* a fetch over one admitted connection), `a_dead_pooled_connection_is_redialed_transparently`, `concurrent_fetch_and_exchange_share_one_dial` (cold cache, multi-thread — proves the slot dedup, not just multiplexing), `a_pooled_connection_idle_past_the_server_bound_is_redialed`, plus `peer_connections`' two pure pruning tests. Server-side counting uses a new `#[cfg(test)]`-only cumulative `accepted_total` on `ConnectionLimiter` — it bounds nothing and does not exist in a real build. Bug-catch proofs: forcing every acquire to dial fresh fails the reuse test (`left: 3 right: 1` admitted connections) and the concurrent test (`left: 3 right: 2`); removing the liveness check and the re-dial fails both re-dial tests on `the operation after a dead pooled connection must still succeed`. `three_node_alpn_convergence` and the T24/T26/T41 suites were each run 3× in isolation, green.
>
> **Residuals.** (a) The `open_bi`-fails-on-a-live-looking-pooled-connection path is a genuine race and has no deterministic test — it is covered by construction and by the two tests that exercise the same invalidate-and-re-dial code through the liveness check. (b) Head-of-line blocking between one peer's concurrent operations on a shared connection is new; the alternative (concurrent stream tasks) needs a per-connection stream cap to keep M-16's memory bound, which means a new limit and belongs with T38's config surface if it is ever wanted. (c) The tidy-close drain covers the last stream of a connection only; earlier streams are finished (not reset) and their peer had already read every reply it asked for before closing its half.
>
> **This closes the T42/T43/T44 follow-up set** — the last three open rows in this tracker's summary table. No row in the summary table is ☐ any more (T33 stands at its documented **interim** ☑, with the authorship format bump still open on its own terms); what remains open is the 0902 register itself (`SECURITY_AUDIT_0902.md`), not this document.
- **Change:** `fetch_want` and `exchange_with_peer` open a fresh `endpoint.connect(...)` on every gossip fetch and every anti-entropy tick. A per-peer connection cache (reused across both call sites, re-dialed on drop/error, liveness-checked) removes the repeated QUIC handshake cost.
- **Priority:** low — **not a security fix.** T23's fetch semaphore bounds concurrent dials and T24 added connect/I-O timeouts + concurrency, so the flood and stall vectors are already closed; this is pure handshake-overhead reduction. Carries real lifecycle risk (shared mutable connection state across the gossip and anti-entropy paths, re-dial races), so it is deliberately isolated from the security tasks.
- **Verify:** repeated fetches/exchanges to one peer reuse a single connection; a dropped connection transparently re-dials; concurrent fetch + exchange to the same peer do not corrupt shared state.
